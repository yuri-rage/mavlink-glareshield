# MAVLink Test Suite & pymavlink Cross-Checks

This directory contains test suites for Glareshield's MAVLink protocol engine, verifying behavior against both unit test specifications and **pymavlink** (the official Python reference implementation):

1. **`mavlink.test.ts`**: Full protocol unit test suite covering MAVLink v2/v1 framing, CRC-X25 accumulation, parser recovery, MAVFTP file transfers, binary unpackers (`param.pck`, `mission.dat`, `fence.dat`, `rally.dat`), telemetry store isolation, and unit formatting.
2. **`golden.test.ts`**: Cross-implementation golden vector verification. Checks the TypeScript decoder, encoder, and CRC table directly against independent vectors generated by `pymavlink` (`vectors.json`).
3. **`check_mock_bridge.py`**: Integration check that connects to `bridge/bridge.py --mock` over WebSocket, decodes all live telemetry packets using `pymavlink`, and verifies field ranges and values.
4. **`ftp_ardupilot.test.ts`**: MAVFTP client against a simulated vehicle that follows ArduPilot's `GCS_FTP.cpp` and `AP_Filesystem_Mission.cpp` (reply `seq = request + 1`, same-seq resend cache, one open file per session, regenerated `mission.dat` on read-back), on clean and lossy links.
5. **`regressions.test.ts`**: QGC `.plan` files as QGroundControl writes them for ArduPilot (takeoff and land-start without coordinates, fixed-wing and VTOL landing patterns), the 720-byte RTCM fragmentation edge, and version polling against a vehicle that never answers.
6. **`check_bridge_security.py`**: Starts the mock bridge and checks the WebSocket Origin allowlist (including `Origin: null`) and that the bridge's NTRIP client can't be used as a relay to arbitrary local ports or have request lines injected.
7. **`check_bridge_udp_target.py`**: Runs the bridge in UDP mode with a simulated vehicle and a simulated second GCS (e.g. Mission Planner) on the same port, and checks that Glareshield's commands only ever go to the vehicle.

## Running Tests

### Standard Test Suite (No Python required)
Runs both unit tests and golden vector tests:
```bash
npm test
```

### Mock Bridge Live Verification (Requires Python + pymavlink)
Validates that `bridge/bridge.py --mock` sends packets matching pymavlink schemas:
```bash
python3 tests/check_mock_bridge.py
# Or verify against an existing bridge instance:
python3 tests/check_mock_bridge.py --url ws://127.0.0.1:56781
```

### Review Regression Checks
These encode behaviour verified against ArduPilot and QGroundControl source. They are kept out of `npm test` until the corresponding fixes land; move them in once they pass.
```bash
npm run test:review          # all three
npm run test:ftp-sim         # MAVFTP vs simulated ArduPilot
npm run test:regressions     # .plan parsing, RTCM edge, version polling
npm run test:bridge-security # needs: pip install websockets
```

Unlike the mock bridge (which echoes the request `seq`), the simulator in `ftp_ardupilot.test.ts` answers with `seq + 1` exactly as ArduPilot does, so it is the one to trust for sequence handling.

### Regenerating Golden Vectors
Only needed when adding new message decoders or updating to a newer pymavlink dialect:
```bash
python3 tests/gen_vectors.py
```

## What's Covered in Golden Tests

* **CRC Table (`crc_extra`)**: Every entry in `MAVLINK_MESSAGE_CRC_EXTRA` matched against `ardupilotmega` dialect seeds.
* **Message Decoders**: Decodes pymavlink wire packets for `HEARTBEAT`, `SYS_STATUS`, `ATTITUDE`, `SCALED_IMU`, `RAW_IMU`, `HIGHRES_IMU`, `GLOBAL_POSITION_INT`, `GPS_RAW_INT`, `VFR_HUD`, `BATTERY_STATUS`, `AUTOPILOT_VERSION`, `STATUSTEXT`, `PARAM_VALUE`, `COMMAND_ACK`, `MISSION_CURRENT`, `MISSION_COUNT`, `MISSION_ITEM`, `MISSION_ITEM_INT`, and `MISSION_ACK`.
* **Sentinels & Boundaries**: Verifies unknown heading, unmeasured battery current/voltage, and zero-truncated MAVLink 2 frames.
* **Message Encoders**: Verifies byte-level payload alignment and CRC-X25 calculation across all `MavlinkEncoder` methods.
* **MAVFTP**: Validates packet payload formatting (`packFtpMessage`) and chunk parsing (`parseFtpPayload`).
